## M1 — 업무 화면에서 첫 의뢰를 읽고 탐색을 시작한다

상태: 2026-09-11 구현 완료. Godot 4.7.1에서 에디터 로드, 프로젝트 실행, M1 핵심 행동 시나리오를 검증했다. 최종 가독성과 클릭 흐름은 아래 직접 확인 항목으로 남긴다.

기준: GAME.md, STORY.md의 수정본과 TECH.md. 첫 의뢰 `SR-001`만 구현한다. 실제 프로젝트 루트와 기존 파일을 먼저 확인하고, 이미 정상 동작하는 프로젝트가 있으면 새 프로젝트로 덮어쓰지 않는다.

### Goal

Godot에서 실행 → 업무용 Desktop → PostOne 의뢰 읽기 → 의뢰의 탐색 링크로 FindOn 화면에 도착하는 하나의 행동을 완성한다.

### 구현 기능

- 설치된 Godot 버전: `4.7.1.stable.official.a13da4feb`.
- Main과 고정 Desktop, Browser/PostOne 표시 전환.
- PostOne 첫 의뢰 1통, S-LINK의 업무 범위와 초기 계정 정보 표시.
- 직원 실명 비식별화·원본·재업로드 삭제라는 의뢰 범위 표현.
- 첫 의뢰 텍스트와 표시값을 chapter_01.json에서 읽는 최소 ContentCatalog.
- SessionState의 의뢰 읽음 상태와 Main의 초기화/연결.
- 메일 또는 S-LINK의 링크로 FindOn 시작 화면 이동. 실제 검색은 M2에서 구현한다.
- 임시로 읽을 수 있는 레이아웃. 잠정 작업 화면은 1280×720으로 시작하고 Container/anchor를 사용한다. 최종 해상도 확정이 아니다.

### 이번 단계에서 구현하지 않을 것

- 검색 결과·웹페이지 본문·사진 비교·대상 등록·실제 수정/삭제.
- 의뢰 완료 판정·답신·공포 연출·후속 의뢰.
- 창 이동/리사이즈, 다중 탭, 세이브, 최종 그래픽·음향.
- 아직 사용하지 않는 메서드·모듈·데이터 항목의 빈 구현.

### 완료 조건

1. 프로젝트가 실행되고 스크립트/리소스 로딩 오류가 없다.
2. Browser/PostOne을 오가도 의뢰 내용과 읽음 상태가 유지된다.
3. 의뢰에서 '무엇을 조사하고 무엇을 처리해야 하는지' 확인할 수 있다.
4. 초기 계정 정보가 한 곳의 데이터에서 동일하게 표시된다.
5. 의뢰 링크를 누르면 FindOn 화면에 도착한다.
6. 후반 비밀·새 인물·새 보상·미정 신분이 추가되지 않았다.

- 돌아와도 의뢰가 사라지거나 두 번 생성되지 않는지.
- 실제 검색은 아직 없다는 단계 범위가 분명한지.

## M2 — 검색과 이미지 추적으로 재업로드를 찾는다

선행 조건: M1 완료. 이번 Milestone은 검색 → 웹 탐색 → 비교까지 완성한다.

### Goal

초기 의뢰의 정보로 TalkBoard를 찾고, blueframe·PicBox 원본을 근거로 MyRoom의 동일 사진을 발견한다.

### 구현 기능

- JSON 기반 검색 필드·별칭, 결과 순서, 빈 검색/결과 없음.
- 공통 WebPageView와 고정 블록 표시.
- 첫 의뢰 페이지 5개: TalkBoard 게시물, PicBox 원본, MyRoom HOME/PHOTO/선택 DIARY.
- 가상 주소 입력, 링크 이동, 뒤로/앞으로, 스크롤 위치 복원.
- C동·차량·개인정보 노출 요소를 확인할 수 있는 테스트 사진 1종.
- 원본/재업로드는 서로 다른 이미지 ID로 등록하고 동일 시각 자료를 재사용.
- 방문 페이지·보인 처리 항목 기록.
- 기존 페이지의 글·링크·검색 항목을 JSON만 바꿔 추가할 수 있는지 확인.

### 이번 단계에서 구현하지 않을 것

- S-LINK 대상 등록·처리·완료, 자동 단서 연결 팝업.
- OCR·이미지 자동 판별·비교 미니게임·추리판.
- 오타 교정 엔진·실제 검색·무관한 사이트/가짜 분량.
- 최종 사진과 사이트 디자인의 제작 완료.

### 생성/수정할 주요 파일

- scenes/ui/web_page_view.tscn
- scripts/ui/web_page_view.gd
- scenes/ui/browser.tscn, scripts/ui/browser.gd
- scripts/content_catalog.gd, scripts/session_state.gd, scripts/main.gd
- content/chapter_01.json
- assets/images/ch01_facility.*
- ROADMAP.md

### 완료 조건

1. 화면에서 얻은 기업명·게시물 표현·blueframe·파일명과 그 조합으로 관련 결과를 찾는다.
2. 기업명 검색 → 게시물 → 원본 → 닉네임/파일명 재검색 → 개인 홈/사진의 경로가 동작한다.
3. 원본과 재업로드의 시각적 동일성, 서로 다른 게시 위치를 플레이어가 비교할 수 있다.
4. 결과 없음·없는 주소에서 돌아올 수 있다.
5. 같은 경로를 여러 번 오가도 기록·스크롤이 정상이며 데이터 로딩 오류가 없다.
6. 테스트용 기존 형태 페이지를 데이터만으로 추가해 연결·검색되는지 확인하고, 검증용 콘텐츠는 최종 의뢰에서 제거한다.

### 내가 Godot에서 직접 확인할 항목

- 다음 검색어를 찾는 근거가 화면에 있는지, 정확한 문장 암기를 요구하지 않는지.
- 결과를 비교해서 고르는지, 위에서부터 무작정 누르고 있지는 않은지.
- blueframe이 누구인지, 어디서 원본을 찾았는지 스스로 설명할 수 있는지.
- 사진을 볼 수 있을 만큼 충분히 크고 출처를 쉽게 오갈 수 있는지.
- 선택 DIARY를 보지 않고도 재업로드까지 찾을 수 있는지.

## M3 — 조사한 대상을 등록하고 처리 범위를 정한다

선행 조건: M2 완료.

### Goal

플레이어가 원본·재업로드·본문 실명을 구분해 S-LINK에 등록하고, 올바른 작업 종류를 선택한다.

### 구현 기능

- Browser 가상 주소 복사, S-LINK 주소 입력과 항목 미리보기.
- 페이지의 항목 선택 → 작업 선택 → 대상 등록, 등록 취소.
- 본문 실명/이미지 ID 단위의 대상 매핑.
- mission의 허용 대상·작업 검증, 범위 밖/미방문/중복 등록 거부.
- 등록된 대상의 위치·내용·작업을 다시 확인할 수 있는 UI.
- 데이터 참조·target ID·허용 작업 불일치 검증.

### 이번 단계에서 구현하지 않을 것

- 실제 비식별화·이미지 삭제·완료 보고·공포 연출.
- 자유 텍스트 편집, 이미지 영역 편집, 자동 정답 대상 등록.
- 범용 권한·직무·신뢰도 시스템.

### 생성/수정할 주요 파일

- scenes/ui/work_order_view.tscn, scripts/ui/work_order_view.gd
- scripts/ui/browser.gd
- scripts/session_state.gd, scripts/content_catalog.gd, scripts/main.gd
- content/chapter_01.json
- ROADMAP.md

### 완료 조건

1. 조사한 세 처리 항목을 개별 등록할 수 있다.
2. 이미지에는 이미지 삭제, 실명에는 비식별화가 대응한다.
3. DIARY·전체 계정·게시물 전체 삭제·잘못된 주소는 등록/승인되지 않는다.
4. 중복 클릭으로 같은 항목이 늘어나지 않는다.
5. 등록 취소와 앱 전환 후 목록 유지가 동작한다.
6. 등록만으로 콘텐츠가 변경되거나 의뢰 완료가 표시되지 않는다.

### 내가 Godot에서 직접 확인할 항목

- 어디에 있던 무엇을 처리하려는지 미리보기로 알아볼 수 있는지.
- TalkBoard 연결 사진과 PicBox 원본을 별개의 복사본으로 잘못 세지 않는지.
- 실수한 등록을 실행 전에 바로잡을 수 있는지.
- S-LINK가 아직 못 찾은 MyRoom의 정확한 주소를 먼저 알려주지는 않는지.

## M4 — 수정/삭제 결과를 확인하고 업무를 보고한다

선행 조건: M3 완료.

### Goal

세 가지 승인 작업이 실제 페이지를 바꾸고, 모든 필수 처리를 완료한 경우에만 보고가 성공한다.

### 구현 기능

- 지정 실명 블록 비식별화, 개별 이미지 상태 삭제.
- 처리 후 열려 있는 화면과 뒤로/앞으로 방문 시 최신 상태 반영.
- 원본 삭제 시 TalkBoard 연결 이미지 동시 소멸, MyRoom 복사본 유지.
- 복사본 별도 처리, 중복 처리의 무해한 거부.
- 세 처리 결과에 따른 보고 가능 여부와 실제 보고 재검증.
- 조기 보고의 범위 안내, 완료 답신 1회 추가.
- 처음부터 다시 시작하여 초기 상태 복원.

### 이번 단계에서 구현하지 않을 것

- 썸네일 공포 이벤트·후속 Chapter·권한 상승·새 보상.
- 실제 에셋 파일 삭제·원본 JSON 덮어쓰기·디스크 세이브.
- 모든 처리를 자유롭게 되돌리는 Undo 시스템.

### 생성/수정할 주요 파일

- scripts/session_state.gd, scripts/main.gd
- scripts/ui/web_page_view.gd, scripts/ui/browser.gd
- scripts/ui/work_order_view.gd, scripts/ui/mail_view.gd
- content/chapter_01.json
- 관련 UI 장면과 ROADMAP.md

### 완료 조건

1. 실명만 바뀌고 게시물의 나머지 문장·댓글·작성자는 유지된다.
2. PicBox 삭제로 TalkBoard의 연결 이미지도 없어지지만 MyRoom 재업로드는 남는다.
3. 원본 먼저/재업로드 먼저 어느 순서로 처리해도 완료할 수 있다.
4. 원본을 일찍 지워도 게시자·메타정보로 추가 조사를 계속할 수 있다.
5. 세 처리 중 하나라도 빠지면 보고가 실패하고, 세 가지 후에는 성공한다.
6. DIARY 생략 여부는 완료 판정에 영향이 없다.
7. 보고·처리 버튼 재클릭으로 답신이나 완료 상태가 중복되지 않는다.
8. 재시작하면 원래 실명·두 이미지·메일 상태가 복구되며 원본 파일은 변하지 않는다.

### 내가 Godot에서 직접 확인할 항목

- 처리 전후의 차이가 눈에 보이는지.
- 원본 삭제만으로 일이 끝났다고 착각했을 때, 추가 조사 이유를 이해할 수 있는지.
- 순서를 바꾸어 플레이해도 막히지 않는지.
- '사진 전체를 없앴다'는 행동의 의미가 설명문 없이 전달되는지.
- 완료 답신이 현재의 친절하고 업무적인 담당자 태도를 유지하는지.

## M5 — 작은 이상현상과 5~15분 핵심 루프를 검증한다

선행 조건: M4 완료.

### Goal

삭제 직후 썸네일 잔여 연출을 더하고, 처음 보는 사람이 핵심 루프를 이해하고 즐기는지 확인한다.

### 구현 기능

- ch01_cache_event.gd와 Main 아래 단일 이벤트 노드.
- 마지막 필수 이미지 처리 후, 관련 FindOn 결과가 실제 보일 때만 1회 썸네일 노출.
- 처리 위치 재확인용 링크와 정상적인 결과 화면 재방문 동선.
- 썸네일 클릭 시 삭제 상태, 화면 이동/타이머 종료의 안전한 처리.
- 최소 가독성·입력/스크롤·페이지 간 이동 불편 수정.
- Windows 로컬 export와 JSON/이미지 포함 확인. Steam 연결은 하지 않음.

### 이번 단계에서 구현하지 않을 것

- 추가 점프스케어·글리치·CCTV/VHS 영상·새 미스터리.
- 모든 공포 이벤트를 위한 범용 시스템.
- 플레이타임을 늘리기 위한 인위적인 로딩/대기.
- 최종 UI/사운드 전체 제작, 모든 플랫폼/해상도 대응.

### 생성/수정할 주요 파일

- scripts/events/ch01_cache_event.gd
- scenes/main.tscn, scripts/main.gd
- scripts/ui/browser.gd, scripts/session_state.gd
- 필요한 UI/콘텐츠 미세 조정
- export_presets.cfg, project.godot — export 포함 설정에 필요한 경우
- ROADMAP.md — 플레이 관찰 결과와 알려진 문제

### 완료 조건

1. 연출은 삭제 이후 관련 결과 화면에서 1회만 보인다.
2. 원본은 복구되지 않으며 클릭해도 삭제된 상태다.
3. 다른 화면에 있는 동안 연출이 몰래 소진되지 않는다.
4. 뒤로/앞으로·앱 전환·빠른 클릭·재시작에서 타이머/노드 오류가 없다.
5. 실제 Windows export에서도 콘텐츠 JSON과 이미지가 로딩된다.
6. 사전 설명을 최소화한 첫 플레이에서 5~15분을 목표로 측정한다. 범위를 벗어나면 원인을 기록하고, 시간만 맞추는 조정은 하지 않는다.
7. 아래 여섯 질문에 대한 플레이 관찰과 답을 기록한다. '재미 검증 완료'는 자동 테스트 결과로 선언하지 않는다.

### 내가 Godot에서 직접 확인할 항목

- 검색: 내가 얻은 정보로 다음 검색어를 떠올렸는가?
- 탐색: 다음 페이지를 선택한 이유를 설명할 수 있는가?
- 단서: 원본과 재업로드를 연결했을 때 발견의 만족감이 있었는가?
- 처리: 대상과 범위를 판단했는가, 안내받은 버튼만 눌렀는가?
- 스토리: 왜 사진 전체까지 지웠는지 스스로 의문이 들었는가?
- 공포: 썸네일이 버그처럼만 느껴졌는가, 자연스러운 작은 이상함으로 느껴졌는가?

### 플레이 관찰 기록 방법

외부 분석 SDK 없이 수동으로 기록한다. 가능하면 내용을 모르는 1~3명에게 플레이하게 한다. 한 번의 테스트로 재미가 입증됐다고 보지는 않는다.

| 항목 | 기록할 것 |
|---|---|
| 시간 | 의뢰 시작→재업로드 발견→처리 완료→보고까지 실제 소요 |
| 검색 | 사용자가 입력한 표현, 막힌 표현, 별칭 보완 필요 여부 |
| 동선 | 다음 링크를 못 찾은 위치, 설명이 필요했던 지점 |
| 판단 | 원본/연결 이미지/복사본 차이를 이해했는지 |
| 스토리 | blueframe과 사진 삭제 목적에 대해 스스로 말한 내용 |
| 이상현상 | 보았는지, 어떻게 해석했는지, 반복 버그가 있는지 |
